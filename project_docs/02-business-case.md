# 旅行规划业务拆解

TravelAgent 的业务主线是“从自然语言旅行需求到可执行旅行方案”。该业务足够真实：用户需求模糊、约束多、信息变化快、需要工具、需要检索、需要多轮沟通，也适合引入多 Agent 协作和评估。

## 用户任务

用户通常不会一次性给出完整需求，常见输入包括：

- “暑假想带孩子去云南玩一周，帮我规划一下。”
- “下个月去东京 5 天，预算 1 万，想吃好一点。”
- “我爸妈第一次出国，想轻松、安全，不要太累。”
- “临时出差去上海，两天空闲，帮我安排一下。”

## 核心业务对象

| 对象 | 说明 | 示例字段 |
| --- | --- | --- |
| 用户画像 | 长期偏好和限制 | 饮食偏好、体力、酒店档次、语言能力、过敏/禁忌 |
| 旅行需求 | 本次旅行约束 | 出发地、目的地、日期、天数、人数、预算、主题 |
| 候选目的地 | 可选择地点 | 城市、季节、签证、交通、预算水平 |
| 行程项 | 每天具体安排 | 时间、地点、交通、费用、备注 |
| 工具结果 | 外部信息 | 天气、汇率、景点开放时间、交通耗时 |
| 评估结果 | 方案质量判断 | 约束满足率、风险、事实依据、预算偏差 |

## 业务流程

1. 接收自然语言需求。
2. 抽取结构化旅行需求。
3. 检查缺失字段并追问。
4. 查询目的地和外部信息。
5. 制定候选规划。
6. 估算预算和时间。
7. 检查风险和约束冲突。
8. 生成最终方案。
9. 用户反馈后修改。
10. 保存偏好和可复用经验。

## 为什么适合教学 Agent

| Agent 技术 | 旅行业务中的自然落点 |
| --- | --- |
| Prompt Engineering | 控制输出格式、语气、假设说明 |
| Structured Output | 抽取日期、预算、人数、偏好 |
| Tool Use | 查天气、汇率、交通、景点 |
| ReAct | 动态决定下一步查什么 |
| Planning | 把大任务拆成研究、安排、预算、审查 |
| RAG | 使用目的地知识库和攻略材料 |
| Memory | 记住用户喜欢轻松、不吃辣、偏好精品酒店 |
| Multi-Agent | 研究员、规划师、预算员、审稿员协作 |
| MCP | 把工具做成统一可发现服务 |
| Evaluation | 判断行程是否满足预算、时间和偏好 |
| Production | 面向用户提供 Web/API 服务 |

## 课程中的最小数据集

建议第一版内置 mock 数据，避免一开始依赖真实外部 API：

- `agent/data/mock/weather.json`：天气查询结果。
- `agent/data/mock/exchange_rates.json`：汇率。
- `agent/data/mock/places.json`：目的地和景点。
- `agent/data/mock/hotels.json`：酒店档位。
- `agent/data/mock/transport.json`：交通耗时和费用。
- `agent/data/eval/travel_requests.jsonl`：评估任务。
