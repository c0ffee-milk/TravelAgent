# Lesson 01：需求澄清

本节课开始给 TravelAgent 增加第一项核心 Agent 能力：需求澄清。用户通常不会一次性给出完整旅行信息，所以 Agent 需要识别已知字段、缺失字段，并决定下一轮应该问什么。

本节仍然不实现完整对话程序。你的目标是理解需求澄清的规则，并在 `agent/` 中为后续实现留下清晰模块边界。

## 本节目标

完成本节后，你应该能够：

- 判断一次旅行需求中哪些信息已经明确。
- 找出会影响规划质量的缺失字段。
- 区分必须追问、可以稍后追问、可以暂时假设的信息。
- 设计一轮最多 2-3 个关键澄清问题。
- 理解 `agent/src/travel_agent/clarification.py` 后续应该承担什么职责。

## 基础知识

### 1. 需求澄清不是表单填写

用户不会愿意一开始回答十几个问题。好的 Agent 应该只追问最影响下一步规划的信息。

例如用户说：

```text
下个月想和女朋友去日本玩 5 天，预算 12000，希望轻松一点。
```

已知信息：

- 目的地：日本。
- 时间：下个月。
- 天数：5 天。
- 同行人：情侣，通常是 2 人。
- 预算：12000。
- 节奏：轻松。

关键缺失：

- 从哪里出发？
- 预算是否包含机票和酒店？
- 日本范围很大，优先东京还是关西？

不应该第一轮就问：

- 每天几点起床。
- 每顿饭预算。
- 是否购物。
- 每个景点停留多久。

### 2. 槽位

槽位就是 Agent 需要维护的结构化字段。第一版 `TravelRequest` 可以关注：

| 字段 | 重要性 | 说明 |
| --- | --- | --- |
| `destination` | 必填 | 目的地或候选目的地 |
| `origin` | 必填 | 出发城市 |
| `date_range` | 必填 | 具体日期或时间范围 |
| `days` | 必填 | 旅行天数 |
| `travelers` | 必填 | 人数和关系 |
| `budget` | 重要 | 总预算 |
| `budget_scope` | 重要 | 是否包含大交通和酒店 |
| `pace` | 重要 | 轻松、适中、紧凑 |
| `themes` | 可选 | 美食、亲子、自然、文化等 |
| `constraints` | 重要 | 签证、体力、饮食、交通禁忌 |

### 3. 对话状态

多轮澄清必须记住状态：

- 已知字段。
- 缺失字段。
- 已经问过的问题。
- 用户新回答的信息。
- 当前假设。
- 是否已经可以进入规划。

否则 Agent 会重复提问，或者在信息不足时直接生成不可靠方案。

## 本节要修改的 Agent 模块

本节对应 `agent/` 中的增量是需求澄清模块骨架：

- `agent/src/travel_agent/schemas.py`：继续承载 `TravelRequest` 等业务对象注释。
- `agent/src/travel_agent/clarification.py`：新增需求澄清流程的注释骨架。

当前只写模块边界和 TODO，不实现函数逻辑。后续进入代码课时，再把这些 TODO 转成真实函数。

## 推荐搭建步骤

### Step 1：先读 schemas.py

确认 `TravelRequest` 需要哪些字段。需求澄清模块的输入和输出都围绕它展开。

### Step 2：打开 clarification.py

你应该能看到四类 TODO：

- 从用户输入中识别已知字段。
- 计算缺失字段。
- 根据优先级生成澄清问题。
- 更新对话状态。

### Step 3：手工设计澄清流程

用这个输入练习：

```text
暑假带孩子和父母去云南玩 7 天，想安全轻松，预算 18000。
```

写出：

```text
已知字段：
- destination:
- date_range:
- days:
- travelers:
- budget:
- pace:

缺失字段：
- origin:
- exact_dates:
- traveler_details:
- budget_scope:
- physical_constraints:

本轮追问：
1. ...
2. ...
3. ...

暂时假设：
- ...

进入规划条件：
- ...
```

### Step 4：控制追问数量

本节课先使用一个简单规则：

- 一轮最多问 3 个问题。
- 优先问会阻塞交通、预算、安全的信息。
- 用户已经明确表达的信息不要重复问。
- 可以假设的信息必须记录在 assumptions 中。

## 关键设计取舍

- 不要追求一次问完所有字段。
- 不要把可选偏好当成阻塞条件。
- 不要隐式编造关键约束。
- 如果用户拒绝补充信息，可以生成草案，但必须标注假设和风险。
